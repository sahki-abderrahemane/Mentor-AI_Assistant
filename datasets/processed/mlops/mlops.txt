incident post-mortems. The report serves as a self-contained masterclass for MLOps

1.1
Theory & Mathematical Foundations
In a typical multi-node training setup, hundreds of processes (one per GPU) generate logs
at a rate of thousands of entries per second. Naive synchronous logging, where each log
call performs a disk write or a network send, stalls the compute-intensive training loop.
Asynchronous process isolation decouples log production from consumption using a
lock-free multi-producer queue and a dedicated background consumer thread or process.
The producer never waits for I/O; it merely enqueues a lightweight string reference.
Host-to-device synchronization bottlenecks are particularly insidious. In Py-
Torch, a simple call like loss.item() on a CUDA tensor invokes an implicit cudaStreamSynchronize()
on the default stream. This halts the GPU pipeline until all preceding operations finish,
effectively serialising CPU and GPU execution. Under heavy logging, this can reduce
overall GPU utilisation below 30%. The asynchronous logger avoids such stalls by only
copying data to host when the stream is already synchronised—never inside the hot loop.
Multi-GPU reduction collectives such as All-Reduce and All-Gather are the back-
bone of distributed training.
The ring-All-Reduce algorithm splits the tensor into P
chunks (where P is the number of processes), and each process sends its chunk to its
right neighbour in a logical ring. After P −1 steps of send-receive, each process has
the complete sum. The total data transferred per process is 2P−1
P |tensor|, near-optimal.
However, logging inside a collective callback can cause deadlocks if the logging library
itself uses another collective, or it can introduce latency spikes that violate the tight
communication deadlines of NCCL.

1.5
Real-World Incident: Silent GPU Stall Due to Synchronous
Logging
Situation: An 8-GPU cluster training a large language model suddenly dropped GPU
utilization from 98% to 30%. Throughput fell from 1.2k tokens/s to 300 tokens/s. The
training loop included a line loss_val = loss.item() immediately after computing the
loss, followed by a verbose log message to a local file.
Diagnosis: Profiling with NVIDIA Nsight revealed that the .item() call forced a
cudaStreamSynchronize on the default stream, stalling all 8 GPUs while the CPU per-
formed a slow synchronous disk write. Because the logging was inside the main training
loop, every iteration was serialised. The disk I/O latency (5-10 ms per write) dominated,
causing massive idle bubbles.
Resolution: The team replaced the synchronous log write with the AsyncLogger
class above. The .item() call was kept but decoupled from the disk write by enqueuing
only the floating-point value to the logger. GPU utilization immediately recovered to
95%, and throughput returned to normal.
The incident underscored the necessity of
isolating I/O from the compute-critical path.

Module 4.2 — High-Performance Model Serving
2.1
The Physics of Serving: Roofline Model & Arithmetic Inten-
sity
The performance of any model-serving kernel is bounded by the hardware’s memory
bandwidth and peak compute. The Roofline Model elegantly captures this. Define
arithmetic intensity I =
FLOPs
Bytes transferred from DRAM. The attainable FLOP/s is:
Performance = min (Pcompute, Bmemory × I) ,
where Pcompute is the peak floating-point operations per second (e.g., 312 TFLOPS for an
NVIDIA H100) and Bmemory is the peak memory bandwidth (e.g., 3.35 TB/s). The ridge
point is Iridge = Pcompute/Bmemory.
5

Autoregressive transformer inference is profoundly memory-bound. Each token gen-
eration step must read the entire key-value (KV) cache from memory. For a single at-
tention head with dimension dk and sequence length L, the bytes read are approximately
2 × L × dk × num_heads (keys and values). The compute is ≈2 × L × dk × num_heads
for the dot-product and a softmax. Thus I ≈1, far below the ridge point for modern
accelerators. Consequently, inference throughput is capped by memory bandwidth, not
FLOPs.
2.2
KV-Cache Memory Fragmentation
Each autoregressive step appends new key and value tensors to the KV-cache. Naive
implementations pre-allocate a contiguous region of size Lmax × 2 × dk × num_heads ×
num_layers. For a 70B model with Lmax = 2048, this can consume over 30 GB per
request. However, most real-world requests are much shorter (median 128 tokens), lead-
ing to internal fragmentation: memory reserved but unused. When requests complete
and free their cache, external fragmentation arises, leaving holes unusable by larger re-
quests. The result is out-of-memory (OOM) crashes even when total free memory appears
sufficient.
2.3
PagedAttention: Virtual Memory for KV-Cache
vLLM introduced PagedAttention, which maps logical KV-cache blocks (e.g., 16-token
blocks) onto non-contiguous physical GPU memory blocks, managed by a block table,
analogous to virtual memory paging. This eliminates both internal and external fragmen-
tation. The block size is a critical parameter: too small increases metadata overhead; too
large wastes memory.

2.5
Production Tools: vLLM and Continuous Batching
vLLM is an open-source serving system that implements PagedAttention and continuous
batching. It allows requests to join or leave the batch dynamically, rather than waiting
for the whole batch to finish. This drastically improves throughput and GPU utilisation,
especially under fluctuating workloads.
2.6
Real-World Incident: Cascading OOM Under Dynamic Batch-
ing
Situation: A text-generation service using vanilla HuggingFace Transformers with static
KV-cache allocation experienced frequent OOM failures when traffic spiked. The cache
was pre-allocated for a max length of 2048 tokens, consuming 24 GB per request. Under
load, concurrent requests quickly exhausted the 40 GB GPU memory.
Diagnosis: Memory profiling revealed that over 70% of the allocated KV-cache was
unused because typical requests generated fewer than 200 tokens. The large pre-allocation
caused severe internal fragmentation. Moreover, when requests finished, their freed con-
tiguous blocks could not satisfy incoming requests, leading to external fragmentation.
Resolution: The team migrated to vLLM with a block size of 16 tokens. Memory
overhead dropped by 60%, and the number of concurrent requests supported on the same
GPU increased from 4 to 12. OOM crashes ceased entirely. The incident highlighted the
importance of virtual-memory-inspired memory management in LLM serving.

Activation Outliers and SmoothQuant
In large language models (typically >6.7B parameters), certain hidden state channels
exhibit much larger magnitudes than others—outliers. These outliers cause rmax to be
an order of magnitude higher than the typical activation range, severely coarsening the
quantization bins for the vast majority of values. SmoothQuant addresses this by smooth-
ing the activation outliers into the adjacent weight channels, using a per-channel scaling
factor derived from the activation statistics. After smoothing, the activations become
well-balanced, allowing high-precision INT8 quantization without perplexity degradation.

3.5
Production Tools: ONNX to TensorRT Pipeline
The ONNX (Open Neural Network Exchange) format provides an intermediate repre-
sentation for models.
NVIDIA TensorRT takes an ONNX graph, optimizes it using
layer fusion, kernel auto-tuning, and precision calibration (e.g., INT8), and generates a
platform-specific inference engine. The typical pipeline: PyTorch →ONNX export →
TensorRT builder →optimized engine. For INT8, a calibration step uses a representa-
tive dataset to compute dynamic ranges for each tensor, avoiding per-batch quantization
overhead.
3.6
Real-World Incident: Perplexity Explosion in 13B Model
Situation: A team quantized a 13B-parameter LLM to INT8 using naive per-tensor
quantization. The perplexity on a validation set jumped from 10.2 (FP16) to 45.8, ren-
dering the model unusable.
Diagnosis: Activation statistics revealed that a handful of channels had activations
peaking at 80 while the 99th percentile was 4. The large rmax inflated S, causing most
values to be quantized to the same bin. This is the classic activation outlier problem.
Resolution: Applying SmoothQuant (implemented via the smoothquant library) mi-
grated the outlier magnitude into the corresponding weight rows, balancing the activation
distribution. After re-quantization, the perplexity dropped to 10.4, within 0.2 of FP16.
The team integrated SmoothQuant into the TensorRT calibration pipeline, making it a
standard step for all future LLM deployments.

4.2
Approximate Nearest Neighbour Indices
IVF (Inverted File Index): The vector space is partitioned into C Voronoi cells via
k-means. A query probes the nearest P cells, reducing search scope from N to ≈N × P
C.
HNSW (Hierarchical Navigable Small World): A multi-layer graph is built
where each node appears in layer ℓwith probability 1/Mℓ. The top layers are sparse;
the bottom layer is the dense full graph. Search begins at a top-layer entry point, greed-
ily moves to the nearest neighbour, descends to the next layer, and repeats, achieving
logarithmic complexity.

Real-World Incident: Vector Drift & Embedding Model Hot-Swap
Situation: A customer-facing chatbot using RAG experienced a dramatic drop in re-
trieval accuracy after the embedding model was upgraded from all-MiniLM-L6-v2 to
all-mpnet-base-v2. Users reported that previously relevant documents were no longer
surfaced.
Diagnosis: The new embeddings resided in a different manifold (different dimension-
ality and statistical distribution). Cosine similarity against the old index was meaning-
less. The vector database had over a million vectors indexed with the old embedding.
Re-indexing would take hours, causing unacceptable downtime.
Resolution: The team implemented a staged rollout: both the old and new em-
bedding models ran in parallel. New documents were indexed with the new model, while
queries were sent to both systems and results merged via RRF. This allowed a gradual
transition. Eventually, a background re-indexing job migrated old documents. The inci-
dent led to a design policy: embedding model versions must be stored as metadata, and
the system must support multiple concurrent indices with versioned routing.

Data drift (covariate shift) occurs when P(X) changes but P(Y |X) remains constant.
For example, user demographics shift, but the model’s decision boundary is still valid.
Concept drift occurs when P(Y |X) changes, i.e., the underlying relationship between
features and target shifts. Example: a previously offensive phrase becomes acceptable
slang.

Real-World Incident: Canary Hardware Mismatch
Situation: A team canaried a new model version on a GPU node with an older archi-
tecture (A100) while production ran on H100s. The canary showed excellent latency and
error rates. After full rollout to the H100 fleet, latency spiked by 40% and OOM errors
appeared.
Diagnosis: The canary’s A100 had different memory bandwidth and compute char-
acteristics. The model had been optimised (e.g., kernel autotuning) specifically for that
GPU, and the H100-optimised plan differed. The canary test was invalid because the
hardware was not identical.
Resolution: The canary was re-deployed on a dedicated H100 node.
The team
added hardware-fingerprint checks to the deployment pipeline, ensuring that canary and
production run on identical instance types. The incident reinforced that canary validation
must replicate production infrastructure precisely.

Conclusion
This report has dissected the five critical pillars of production AI systems. Asynchronous
logging eliminates host-device synchronisation stalls, restoring GPU utilisation. Hardware-aware
serving with PagedAttention defeats KV-cache fragmentation and OOM failures. Quan-
tization, especially with SmoothQuant, enables efficient deployment of giant models.
Enterprise RAG systems leverage vector databases and hybrid retrieval to deliver accu-
rate, context-rich generations. Finally, continuous observability with PSI drift detection
and automated canary rollbacks ensures resilience in the face of changing data and mod-
els. Mastery of these topics is essential for any AI systems engineer aspiring to deploy
large-scale, reliable, and cost-effective ML services.
